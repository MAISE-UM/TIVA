TIVA — EHR Integration

How TIVA connects to an EHR with SMART on FHIR: how the pieces fit together, what happens during a launch, and what to configure for the login and for the patient data the dashboard loads.

1. How the pieces fit 2. Before you start 3. Launch flow 4. Register with the EHR 5. Configure the login 6. Patient data 7. Test it 8. Troubleshooting 9. Where things are defined

This page is a high-level guide. The endpoint engine and the full list of seeded endpoints are in api.html § Endpoint engine. Every login setting, with its default, is in api/TIVA_API/Models/EhrSettings.cs, and a complete example is api/deploy/appsettings.example.json.

All site-specific values live in the Ehr section of the API settings and in database rows. Connecting TIVA to an EHR that follows the same data shapes does not need code changes.

1. How the pieces fit together

Login travels as redirects through the browser. Patient data is fetched by the API directly from the EHR, using the user’s EHR token held in the API’s memory.

There are two separate jobs, configured in different places:

JobWhat happensDefined inChanging it needs
LoginThe EHR sends the user to TIVA, the user is authenticated with the EHR, and TIVA signs them in.Code plus the Ehr settings (EhrOAuthController, SmartOnFhirService)Editing settings, then recycling the API
Patient dataThe dashboard asks the API for the patient’s data; the API calls the EHR with the user’s EHR token.Database rows (api.Endpoints and related tables)Editing rows, then POST /Admin/ReloadEndpoints

Two terms are easy to mix up:

  • A route is a URL the TIVA API itself answers, for example ehr/launch. The login routes are mapped when the API starts, with paths taken from Ehr:Routes.
  • An endpoint is a database-defined API call, for example FHIR/GetVitalSigns. All endpoints are served by one generic route, /Api/{schema}/{endpoint}. For REST endpoints, each row tells the API which EHR URL to call and how.

2. Before you start

  • The TIVA API and client deployed and working without the EHR (see api/README.md and client/README.md), with the database built (examples/CreateDB.sql) and seeded (examples/SeedData.sql).
  • A public HTTPS host name for TIVA, for example tiva.example.org. The EHR redirects the user’s browser to it, and the login cookies are Secure with SameSite=None, so plain HTTP does not work.
  • A SMART on FHIR app registration with your EHR vendor (section 4). This is usually done by your hospital’s EHR team, so allow time for it: you cannot test the login until it exists.
  • Access to the EHR’s non-production environment and a test patient with a surgical case.
  • OpenSSL (or another way to create an RSA key pair).

How the URLs fit together

Getting the URLs consistent is the most common setup problem. The example host is tiva.example.org.

About /REST. On a standard Windows deployment, IIS serves the API as an application with the alias REST. IIS removes that prefix before the API sees the request, so inside the API the route is ehr/launch, while the EHR and the browser use /REST/ehr/launch. Paths written as /REST/... on this page are the outside URL.

Where the settings go. On a server, the Ehr settings go in the IIS web.config as MA_* variables; on your own machine they go in appsettings.json. A setting’s JSON path becomes its variable name (Ehr:ClientId is MA_Ehr__ClientId; list items get an index, MA_Ehr__AllowedIssuers__0). If a value is in both places, web.config wins. See api/README.md, section “Which config file do I edit?”. Templates: api/deploy/appsettings.example.json and api/deploy/web.config.example.

3. Launch flow

What happens when a user clicks the TIVA link on a case in the EHR: launch → authorize → callback → /auth/ehrloading → complete → /auth/ehrlaunch → dashboard data pull.

Browser hops are redirects or page navigations. Step 6 is a direct server-to-server call from the API to the EHR. The EHR never talks to the Next.js client, and the browser never sees the EHR tokens.
#WhereWhat
1EhrOAuthController.LaunchThe EHR opens /REST/ehr/launch with iss, launch and the case parameters named in Ehr:LaunchParameters. The API rejects issuers not in Ehr:AllowedIssuers (an empty list accepts all and logs a warning at start-up), reads {iss}/metadata to find the authorize URL, saves the case details under a new random state (kept for 10 minutes), and redirects to the EHR authorize URL.
2EHRAuthorizes the launch and redirects to Ehr:RedirectUrl with code and state.
3EhrOAuthController.CallbackStores the code and state in HttpOnly cookies, then redirects to {JwtAuthentication:ValidIssuer}{Ehr:ClientRoutes:Loading}.
4client/app/auth/ehrloading/page.tsxFetches ehr/client-config to learn the complete path and sends the browser to it on the API.
5EhrOAuthController.CompleteExchanges the code at the token endpoint, authenticating with a JWT signed by Ehr:ClientAssertion:PrivateKey. Validates the id_token. Maps the id_token claim to a TIVA user (section 5), creating it if allowed. Failures redirect to Ehr:ClientRoutes:Failure.
6EhrOAuthController.SignInBuilds TIVA’s own access and refresh JWTs, stores them with the EHR tokens in the in-memory session cache, and sets the login cookies (Secure, SameSite=None, AppSettings:COOKIE_DOMAIN).
7Complete (end)Logs the login (api.UserLogin_Log, including patient ID, MRN and reporter name), sets the readable cookie X-SurgicalID (<case id>||<patient id>), and redirects to Ehr:ClientRoutes:Launched.
8client/app/auth/ehrlaunch/page.tsxNavigates to /?fromEhr=true, which starts the patient data load (section 6).

Standalone launch. GET /REST/ehr/standalone sends a user to the EHR authorize page without a patient context (Ehr:StandaloneScope); /REST/ehr/standalone/callback exchanges the code, validates the id_token, resolves the user with Ehr:StandaloneUser and redirects to Ehr:ClientRoutes:StandaloneLaunched.

Timing limits. The state is remembered for 10 minutes, so the user must finish the login within that time or the case ID is lost. The EHR metadata is cached in memory (60 minutes, renewed each time it is used), so after changing MetadataUrl or MetadataHeaders recycle the API.

4. Register TIVA with your EHR vendor

Create a SMART on FHIR app with your EHR vendor (or ask your EHR team to) and give them:

ItemValue
Launch URLhttps://<your TIVA host>/REST/ehr/launch
Redirect URIhttps://<your TIVA host>/REST/ehr/callback
JWK Set URLhttps://<your TIVA host>/REST/.well-known/jwks.json
Scopesopenid fhirUser profile launch, plus read access to the FHIR resources and EHR web services TIVA reads (section 6)

Ask the EHR team to configure the launch so that it passes the surgical case ID and the user’s first and last name as query parameters, and note what they are called (the example config uses SurgeryID, ReporterFirstName and ReporterLastName). If the app is already registered under other paths, do not change the registration; set Ehr:Routes to match.

The registration gives you values you need in the next section:

You receiveGoes into
Client IDEhr:ClientId
The EHR’s token issuer nameEhr:Issuer
The URL of the EHR’s public signing keys (JWKS)Ehr:JwksUrl
The URL of the EHR’s FHIR metadataEhr:MetadataUrl
The names of the launch query parametersEhr:LaunchParameters
(Optional) The EHR’s FHIR server URL as it appears in iss on a launchEhr:AllowedIssuers (can start empty; set it in production)

If the EHR publishes OpenID Connect configuration at <issuer>/.well-known/openid-configuration, its issuer and jwks_uri fields are the values for Ehr:Issuer and Ehr:JwksUrl. The FHIR metadata is normally at <FHIR base URL>/metadata. AllowedIssuers is normally the metadata URL without the trailing /metadata; to confirm it, read the iss query parameter of a test launch in the IIS request log or the browser’s network tab.

Client assertion key pair

To get tokens, TIVA proves to the EHR that it is the registered app by signing a short-lived JWT with a private key. The EHR checks the signature with the matching public key, which it downloads from the JWK Set URL you registered.

openssl genrsa -out ehr-private.pem 2048
openssl req -new -x509 -key ehr-private.pem -out ehr-public.pem -subj "/CN=tiva" -days 3650
  • Put ehr-private.pem in Ehr:ClientAssertion:PrivateKey. Never commit it.
  • Put ehr-public.pem (an X.509 certificate) in Ehr:ClientAssertion:PublicCertificate. TIVA publishes it at /.well-known/jwks.json for the EHR to fetch.
  • In JSON, write PEM line breaks as \n. In web.config the value can contain real line breaks.
  • The assertion is signed with Algorithm (default RS384) and valid for LifetimeMinutes (default 2). If the EHR identifies keys by kid, Kid must match what the EHR has on file; set IncludeKidHeader to false if the EHR does not want it.

5. Configure the login

This is the smallest Ehr section for a typical EHR. Anything left out takes the default from Models/EhrSettings.cs.

"Ehr": {
  "Enabled": true,
  "DisplayName": "EHR",
  "ClientId": "<client ID from the app registration>",

  "Issuer": "https://ehr.example.org/oauth2",
  "JwksUrl": "https://ehr.example.org/oauth2/jwks",
  "MetadataUrl": "https://ehr.example.org/fhir/metadata",
  "AllowedIssuers": [ "https://ehr.example.org/fhir" ],

  "RedirectUrl": "https://tiva.example.org/REST/ehr/callback",

  "ClientAssertion": {
    "PrivateKey": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----",
    "PublicCertificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
    "Kid": "ehr"
  }
}

Also check the values in the URL table: JwtAuthentication:ValidIssuer (with trailing /), AppSettings:COOKIE_DOMAIN, AppSettings:SITE_URL, AppSettings:AUTH_JKU_URL, and the client’s NEXT_PUBLIC_EXTERNAL_API_BASE_URL.

Main settings

SettingMeaning
EnabledDefault false. When false, none of the EHR login routes exist (they return 404).
DisplayNameName shown in dashboard messages and saved as the login source in the login log.
ClientId, Issuer, JwksUrlUsed to validate the id_token (audience, issuer, signature). Issuer must match exactly.
AllowedIssuersThe iss values a launch may come from (case and trailing / ignored). Others get HTTP 403. Empty means any issuer is accepted, with a warning at start-up.
MetadataUrl, MetadataHeadersFHIR metadata URL, used when there is no iss (standalone launch, token refresh), and optional extra headers to send when downloading it ({ClientId} is replaced with the client ID). Some EHRs need a vendor-specific header here; check your EHR’s documentation.
EndpointDiscoveryHow the authorize and token URLs are found in the metadata (rest[0].security.extension): ByUrl (default) matches entries named authorize and token; ByIndex takes the first and second entry, for EHRs that do not label them.
RedirectUrlMust exactly match the registered redirect URI.
LaunchScope, StandaloneScopeScopes requested on an EHR launch and on a standalone launch.
TokenRefreshMinutesDefault 45. The EHR access token is refreshed when older than this; set it below the EHR’s token lifetime.
Routes:*, ClientRoutes:*Paths of the API login routes and of the client pages they redirect to. Defaults are ehr/launch, ehr/callback, ehr/complete, auth/ehrloading, auth/ehrlaunch, and Search for failures. Change Routes if your app is registered under other paths.
LaunchParameters:*The query-string names the EHR adds to the launch URL: CaseId, FirstName, LastName. Without the case ID the login works but no patient data loads.

Mapping the EHR user to a TIVA user

After the id_token is validated, Ehr:User (EHR launch) and Ehr:StandaloneUser (standalone launch) control how a TIVA user name is derived and found:

SettingDefault (User)Meaning
ClaimTypepreferred_usernameWhich claim of the id_token holds the user name.
StripPrefixes[]If the value starts with one of these (ignoring case), the first match is removed.
LowercasefalseConvert the result to lower case.
FallbackSuffixes[]Tried in order if the plain name is not found.
AutoCreatetrueCreate the TIVA user if no match is found. If false, the login fails.
DefaultRoleId2Role of a created user (seed data: 1 Administrator, 2 User). It must be allowed to call the FHIR endpoints (section 6).

StandaloneUser has the same settings but defaults to Lowercase: true and AutoCreate: false. For example, with StripPrefixes: ["HOSPITAL\\"], Lowercase: true and FallbackSuffixes: ["@hospital.org"], the claim HOSPITAL\JSmith becomes jsmith; if no such user exists TIVA tries jsmith@hospital.org, and then creates jsmith when AutoCreate is on.

What the client reads. GET /REST/ehr/client-config returns Enabled, DisplayName, the Complete path and DataMapping. It contains no secrets, and the login cannot complete without it.

6. Patient data

With ?fromEhr=true the dashboard calls searchFHIR() (client/lib/med-helpers.tsx), which makes up to four calls through the API, in order. It stops at the first one that fails or comes back incomplete, leaving whatever it has loaded so far. The whole load repeats every 5 minutes so new doses appear during the case.

#Client functionAPI endpointMethodWhat it fetches
1getFHIRVitalSignsFHIR/GetVitalSignsGETWeight and height (standard FHIR Observation)
2getEhrSurgicalCaseFHIR/GetSurgicalCasePOSTPatient name, sex, date of birth, MRN; procedure; operating room; anesthesia start and stop times (EHR web service)
3getFHIRMedicationStatementsFHIR/GetMedicationStatementsGETThe patient’s medication orders from 3 days before anesthesia start (standard FHIR MedicationStatement), matched to TIVA drugs by Medication_Search_Terms
4getMedicationAdministrationsFHIR/GetMedicationAdministrationPOSTThe doses given for the matched orders, kept between anesthesia start and end (EHR web service)

The client does not call the EHR itself. It calls TIVA’s generic API, for example GET /REST/Api/FHIR/GetVitalSigns?patient=.... The endpoints are rows in the database, not code. Each uses Credential_Source = UserSession and Credential_Key = FhirAccessToken: before the call the API refreshes the EHR token if it is older than Ehr:TokenRefreshMinutes, then sends the user’s EHR access token as a bearer token to {URL base}{URL}. The browser never receives the EHR tokens. If the user has no session (the API was restarted), the call fails with Authentication Token Invalid and the user relaunches from the EHR. The dose mapping is described in client.html § Dashboard.

Configuring the endpoints

  1. Set the EHR base URL. All FHIR endpoints share one URL base: each endpoint row’s URL_Base column holds a name (seed data: EhrFHIR), and the address is the List_Value of the admin.Application_Lists row with Category = 'APIEditor', Section = 'URLBases' and that name as List_Key. Keep the trailing /. The value is cached for up to 60 minutes and ReloadEndpoints does not clear it, so recycle the API after changing it. 
    UPDATE admin.Application_Lists
SET    List_Value = 'https://ehr.example.org/'
WHERE  Category = 'APIEditor' AND Section = 'URLBases' AND List_Key = 'EhrFHIR';
  2. Fill in the endpoint URLs. No EHR URL paths are seeded: every REST endpoint row (FHIR/GetVitalSigns, FHIR/GetMedicationStatements, FHIR/GetSurgicalCase, FHIR/GetMedicationAdministration and the others the dashboard does not use) has the placeholder REPLACE_WITH_EHR_API_PATH. The first two read standard FHIR resources (Observation, MedicationStatement); the other two call EHR-specific web services. Find the matching resource or service path in your EHR vendor’s API documentation, relative to the URL base, and set it: 
    UPDATE api.Endpoints
SET    URL = '<path from your EHR documentation>'
WHERE  Endpoint_Name = 'FHIR/GetSurgicalCase';
  3. Check the parameters. Each request is defined by rows in api.EndpointParameters (where the parameter goes, who supplies it, a {var} template, a list delimiter, or the signed-in user name). Compare the seeded rows with your EHR’s request format, and keep the names the client sends: patient and effective (statements), SurgicalRecordID (case), and PatientID, ContactID and OrderIDs (administrations).
  4. Check who can call them. api.EndpointSecurity grants the FHIR endpoints to the Administrator (1) and User (2) roles. Users created by the EHR login get Ehr:User:DefaultRoleId, so keep that role allowed.
  5. Reload. After editing endpoint rows, call POST /REST/Admin/ReloadEndpoints as an administrator, or recycle the API.

The data model and editing endpoints are in api.html § Endpoint engine. api/TIVA_API/examples/ExportEhrEndpoints.sql exports all the FHIR rows from a working database, to copy to another site.

A different EHR. The surgical case and medication administration endpoints must return JSON in the shape the client parses in searchFHIR(). An EHR with different services needs equivalent endpoints and, if the response shape differs, changes to that client code.

7. Test it

Work through these in order; each step tests the one before it.

  1. API is up. GET /REST/Admin/Health returns Healthy.
  2. Settings are loaded. GET /REST/ehr/client-config returns Enabled: true and your DisplayName and DataMapping. If not, the Ehr section is not being read; check which config file the server uses.
  3. Keys are published. GET /REST/.well-known/jwks.json lists two keys: your EHR key (with the Kid you set) and the API token key.
  4. Launch. From a test patient’s case in the EHR’s non-production environment, click the TIVA link. The address bar should pass through the EHR, /REST/ehr/callback, auth/ehrloading and /REST/ehr/complete, and end on the dashboard.
  5. Login result. A successful login appears in api.UserLogin_Log. A failure sends you to the Failure page and the reason is in the error log.
  6. Data. In the browser’s network tab, check the calls to /REST/Api/FHIR/... in order. Each response has bSuccess, sErrorInfo and oReturnObject.
  7. Token refresh. Keep the dashboard open longer than TokenRefreshMinutes; the next 5-minute reload should still work.

For development only, with Environment set to Development (never in production), GET /REST/Admin/RestoreSession?username=<user> restores the cookies of a user whose session is cached, so you can reopen the dashboard without launching from the EHR again.

8. Troubleshooting

What you seeLikely cause
/ehr/launch returns 404Ehr:Enabled is not true, or the path differs from Ehr:Routes.
HTTP 403 “Launch issuer not allowed”The launch iss is not in Ehr:AllowedIssuers. The exact value is in the error log.
500 “Internal Auth Security Error:” at launchThe metadata could not be downloaded, or no authorize URL was found in it. Check {iss}/metadata, MetadataHeaders and EndpointDiscovery (try ByIndex).
The EHR shows an error before returning to TIVAThe registration does not match: RedirectUrl, ClientId, scopes or launch URL.
500 “Failed to pull identifier” at ehr/completeThe code cookie did not arrive. Check HTTPS, that AppSettings:COOKIE_DOMAIN matches the host, and that the browser is not blocking cookies.
500 “Internal Auth Error:” at ehr/completeThe token exchange failed. Common causes: the EHR does not accept the client assertion (wrong key pair, Kid or Algorithm, or the JWK Set URL is not reachable by the EHR), RedirectUrl differs from the one used at launch, or the code was already used or expired.
Redirected to the Failure page, log says “EHR Authentication failed”The id_token failed validation: Issuer or ClientId does not match, or JwksUrl is wrong.
Redirected to the Failure page, log says “User not found”The claim named by ClaimType is missing, or no user matches and AutoCreate is false.
Logged in, but no patient data (“EHR launch state not found or expired”)More than 10 minutes between launch and completion, or the API restarted in between. Relaunch.
Logged out after a whileSessions live in memory and expire after 60 minutes without use. Restarting the API ends all sessions.
Authentication Token Invalid or Failed to refresh FHIR tokenThe session is gone, or the EHR rejected the refresh. Relaunch; check that Ehr:MetadataUrl is set, because the refresh needs it.
URL Base Not FoundNo admin.Application_Lists row (APIEditor / URLBases) matches the endpoint’s URL_Base name.
Missing Required Parameters: ...The client did not send a parameter the endpoint requires. Compare the endpoint’s parameter rows with the client function.
The call succeeds but the response is an EHR error messageAn HTTP 401, 403 or 404 from the EHR is returned as the response body with bSuccess true. Read oReturnObject. Typical causes: a wrong URL or base URL, a missing scope or API access on the registration, or wrong parameters.
Changes have no effectURL base changes need an API recycle (cached). Endpoint row changes need POST /Admin/ReloadEndpoints. Ehr setting changes need an API recycle.
The dashboard stays empty after loginThe load stops at the first incomplete step. Check the network tab to find which call returned nothing; usually a DataMapping label does not match, so weight or height is not found.
“Anesthesia Start is not detected”AnesthesiaStartEvent does not match a timing event Title, or the event has not been documented yet.
Some drugs are missingThe drug’s Medication_Search_Terms do not match the order name in the EHR, or the infusion is not yet validated in the EHR.

Hosting notes

  • Sessions (including EHR tokens), OAuth state, the URL base and the endpoint cache are in process memory. Run the API as a single instance; restarting it signs EHR users out and they relaunch from the EHR.
  • GET /REST/.well-known/jwks.json publishes both the EHR client-assertion public key and the API’s token-signing key, so the EHR can verify assertions and the client can verify TIVA tokens.
  • api.UserLogin_Log stores patient identifiers from the launch. Treat the database as holding protected health information.
